# hammieboye-bot

호감도 시스템을 가진 햄스터 페르소나 "햄미"의 디스코드 봇입니다. 슬래시 커맨드 + 호출 단어
기반 자연어 대화를 지원하며, OpenAI Responses API와 Supabase(Postgres)로 동작합니다.

## 기능

- **자연어 대화**: 정해진 호출 단어(`해미야` 등)로 말을 걸면 페르소나에 맞춰 답합니다.
- **슬래시 커맨드**: `/페트병`(미니게임), `/내정보`·`/니정보`(정보), `/내업적`·`/니업적`(업적),
  `/랭킹`(호감도 순위), `/가입`·`/탈퇴`.
- **호감도 시스템**: 상승 5가지(병 던지기, 부름 이벤트, 긍정 감정, 미니게임, 취침 전 대화왕)/
  하락 5가지(과호출, 반복 발화, 부정 감정, 부름 이벤트 무시, 쿨타임 남용)로 매일 갱신됩니다.
  사용자 식별은 Discord user ID 기준 크로스서버 통합입니다.
- **글로벌 이벤트**: 하루 5번 스스로 말을 거는 "부름 이벤트", 자정의 "취침 전 인사",
  06:30 기상과 함께 오는 아침 인사(생일·기념일 포함), 취침 중 맨션 깨움 이벤트.
- **업적 시스템**: 일반/전설 등급의 도전과제, 자연어로 힌트만 얻고 목록은 직접 찾는 방식.
- **관리자 콘솔**: 전용 트리거 문구로 여는 세션형 채팅 명령어(LLM 미사용, 순수 규칙 기반).

기능별 세부 규칙(수치, 확률, 예외 조건 등)은 `CLAUDE.md`에 스펙으로 정리돼 있습니다.

## 구조

```
hammieboye-bot/
├── main.py                 # 진입점: client 생성 + dispatcher 연결
├── config.py                # .env 로드 (필수 항목, 기본값 없음)
├── core/                    # 메시지 처리 파이프라인 + 백그라운드 이벤트
│   ├── dispatcher.py          # on_ready/on_message 라우팅, 스케줄러 부트스트랩
│   ├── chat.py                # 자연어 턴 파이프라인 (본문 참고)
│   ├── intent.py              # RAG 카테고리 분류 + 감정 분류 (단일 API 호출)
│   ├── call_event.py          # 부름 이벤트
│   ├── sleep_event.py         # 취침 전 인사 + 보상
│   ├── wake_event.py          # 취침 중 맨션 깨움 이벤트
│   ├── greeting.py            # 아침 인사 / 생일·기념일
│   ├── admin.py                # 관리자 콘솔 (규칙 기반)
│   └── scheduler.py            # KST 기준 일일/주기 태스크 등록
├── command/                 # 슬래시 커맨드 실제 처리 로직
├── documents/                # RAG 참고 문서 (프로필/명령어/호출단어/호감도가이드/업적)
├── achievements/             # 업적 정의 (파일 1개 = 업적 1개)
├── responses/engine.py       # OpenAI Responses API 호출 (생성)
├── db/                       # Supabase REST/RPC 래퍼 + 테이블별 쿼리 모듈
└── supabase/schema.sql       # 테이블 + RPC 함수 DDL
```

## 설정

```bash
pip install -r requirements.txt
cp .env.example .env   # 값 채우기
python main.py
```

`.env`는 `DISCORD_TOKEN`, `ALLOWED_GUILD_IDS`, `CALL_PREFIXES`, `ADMIN_USER_ID`,
`OPENAI_API_KEY`/`OPENAI_MODEL`/`OPENAI_JUDGE_MODEL`/`OPENAI_MAX_OUTPUT_TOKENS`/
`OPENAI_PROMPT_CACHE_KEY`, `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`를 전부 필수로 요구합니다
(하나라도 없으면 즉시 에러). 값 설명은 `.env.example` 주석과 `CLAUDE.md`를 참고하세요.
Supabase 스키마는 `supabase/schema.sql`을 SQL Editor에 실행해 준비합니다.

## 엔지니어링 전략

이 봇은 OpenAI API 비용과 응답 지연시간이 실사용 규모(다수 서버, 자연어 메시지마다 호출)에서
실제 문제가 됐던 프로젝트라, 아래 전략들을 거치며 설계가 여러 번 바뀌었습니다.

### 1. 모델 계층화로 비용 절감

호출 빈도가 전혀 다른 두 역할에 서로 다른 모델을 씁니다.

- **`OPENAI_MODEL`**(생성 + 분류, 고빈도): 자연어 메시지가 올 때마다 호출됩니다. 페르소나
  답변 생성(`responses/engine.py`)과 RAG 카테고리·감정 분류(`core/intent.py`)가 여기 해당합니다.
- **`OPENAI_JUDGE_MODEL`**(저빈도, 정확도 우선): 하루 5번뿐인 부름 이벤트 응답의 relevant/
  negative/irrelevant 판정, 하루 1번뿐인 아침 인사 생성처럼 호출 횟수가 적어 비용 부담이
  없는 자리에는 판정 정확도가 더 필요해 상대적으로 무거운 모델을 씁니다.

과거엔 매 답변마다 생성 1회 + LLM-as-judge 검수 1회(문제 있으면 재생성까지 최대 3회)를
호출했지만, 이후 judge 패스를 완전히 제거했습니다(§13-C) — 검수용 API 호출 자체가 사라져
메시지당 호출 수가 최대 3회에서 사실상 1~2회로 줄었습니다. 대신 감정 판정은 신설한
`core/intent.py`의 분류 호출에 얹어서 처리해, 기능이 늘어도 호출 횟수는 늘지 않습니다.

응답 생성 전 모델이 소모하는 "추론" 토큰이 `max_output_tokens` 예산을 같이 잡아먹어 답변이
빈 문자열로 잘리는 문제가 있어, 생성·분류 호출 전부 `reasoning={"effort": "none"}`으로
추론 토큰 자체를 0으로 만들어 둡니다.

**호출 자체를 생략하는 고정 응답 경로**도 많습니다: 호감도가 음수, 오늘 자연어 대화 상한
소진, 반복 발화 페널티, 부름 이벤트 진행 중 무관한 잡담 등은 전부 API를 아예 부르지 않고
고정 문구 풀에서 즉시 응답합니다(`core/chat.py`) — 사용자 경험 톤을 맞추는 목적도 있지만,
실질적으로 비용이 드는 경로를 최소화하는 장치이기도 합니다.

### 2. 프롬프트 캐싱

`responses/engine.py`의 `get_response`는 매 호출마다 완전히 동일한 `instructions`
(페르소나 `SYSTEM_PROMPT`)와 `prompt_cache_key`를 사용합니다. OpenAI는 정적 프리픽스가
요청마다 바이트 단위로 똑같고 최소 1,024토큰 이상일 때만 그 부분을 캐시해 입력 토큰 비용을
줄여주므로, **유저 메시지·RAG 컨텍스트·대화 히스토리처럼 매번 달라지는 내용은 절대
`instructions`에 넣지 않고 항상 `input`에만 넣습니다.**

`SYSTEM_PROMPT`를 수정할 때마다 `OPENAI_PROMPT_CACHE_KEY` 값을 같이 올립니다
(`hammieboye-chat-v3` → `v5`) — 캐시 키가 그대로면 이전 프롬프트로 만들어진 캐시가 새
프롬프트와 뒤섞여 캐시 히트를 계산에 넣은 latency/cost 추정이 틀어질 수 있기 때문입니다.

### 3. RAG: 임베딩 없는 카테고리 매칭

문서 개수가 5개(프로필/명령어 목록/호출 단어 목록/호감도 가이드/업적)로 고정돼 있고 앞으로도
크게 늘어날 가능성이 낮아, 벡터 검색 대신 **LLM 분류로 카테고리를 다중 선택**하는 훨씬 가벼운
방식을 씁니다(`core/intent.py`→`documents/__init__.py`):

1. 자연어 메시지 하나당 구조화 출력(JSON Schema) 호출 1번으로 해당 문서 카테고리 전부와
   감정을 동시에 판정합니다 — RAG 판정과 감정 판정을 하나로 묶어 별도 API 호출을 늘리지 않습니다.
2. 매칭된 카테고리의 문서 원문을 그대로 이어붙여, "이 자료에 없는 내용은 지어내지 말고
   모른다고 답해라"는 방지 문구와 함께 `input`의 맨 앞에 참고 메시지로 끼워 넣습니다.
3. 생성 모델은 이 컨텍스트를 근거로만 답하고, `SYSTEM_PROMPT`에도 "확실하지 않은 기능/설정
   질문에 확답하지 말 것"이라는 규칙을 별도로 둬 이중으로 환각을 방지합니다.

임베딩·유사도 검색 인프라 없이, 이미 매 메시지 호출되는 분류기에 라우팅 책임까지 얹는 구조라
추가 인프라나 비용 없이 RAG를 구현했습니다.

### 4. DB: PostgREST 직접 호출 + 원자적 RPC

ORM 없이 Supabase의 PostgREST 엔드포인트를 얇은 `aiohttp` 래퍼(`db/client.py`)로 직접
호출합니다. 단순 CRUD는 REST(`select`/`insert`/`upsert`/`update`/`delete`)로 처리하고,
**동시 요청 사이의 경쟁 조건(race condition)이 실제로 문제가 되는 지점은 전부 Postgres
RPC 함수로 옮겨 원자성을 DB 트랜잭션에 위임**합니다.

- `add_affection`: 일일 +20 획득 상한의 "부분 지급"(예: 이미 +17인 상태에서 +5 이벤트가
  오면 +3만 적용)을 애플리케이션에서 읽고-계산하고-쓰는 대신 SQL 함수 내부에서 한 번에
  처리해, 서로 다른 이벤트가 거의 동시에 들어와도 상한을 넘기지 않습니다.
- `claim_call_event`: 부름 이벤트의 "가장 먼저 반응한 1명" 판정을 `claimed_by IS NULL`
  조건부 UPDATE로 구현 — 여러 서버에서 동시에 응답이 와도 정확히 한 명만 성공합니다.
- `register_sleep_mention`: 취침 중 맨션 깨움 이벤트의 서버별 카운트 증가·임계치 판정·
  1회 발동 처리를 한 RPC로 묶어, 여러 유저가 동시에 맨션해도 카운트 유실이나 중복 발동이
  없습니다 (원래 Python에서 읽고-쓰던 구조를 실사용 중 레이스를 발견하고 이 방식으로 교체).
- `refresh_daily_conversation_caps`: 매일 자정 전체 유저의 자연어 대화 상한을 유저 수만큼
  왕복하는 대신 SQL 함수 한 번으로 일괄 갱신합니다.

업적 지급(`db/achievements.py`)도 "이미 있는지 확인 후 insert"가 동시 요청에서 유일성
제약 위반으로 실패할 수 있는 걸 발견해, 그 예외를 "이미 획득함"으로 안전하게 흡수하도록
방어했습니다.

### 5. 대화 히스토리: 하나의 로그가 세 가지 역할

`chat_history` 테이블에 유저 발화(`role=user`)와 봇 답장(`role=assistant`)을 전부 남기고,
이 한 테이블(과 30분/최대 50개짜리 조회 윈도우)로 서로 다른 세 기능을 동시에 처리합니다.

1. **대화 기억**: 생성 직전 최근 대화 턴(유저+봇, 최대 5턴)을 OpenAI Responses API의
   `input` 메시지 배열 형식 그대로 가져와 문맥을 유지합니다.
2. **분당 과호출 감지**: 고정 1분 버킷 대신 히스토리 타임스탬프를 슬라이딩 윈도우로 스캔해
   분 경계를 걸친 우회(예: 59초와 1초 사이에 20개 전송)를 막습니다.
3. **반복 발화 감지**: 같은 문자열(정규화 후 비교)이 최근 히스토리 안에서 누적 3번 넘게
   나오면 그다음부터 페널티를 적용합니다 — 별도 카운터 없이 같은 로그를 다시 스캔합니다.

감정 판정 결과도 분류가 끝난 뒤 해당 로그 행에 되짚어 기록해서(`set_detected_emotion`),
나중에 실제로 어떤 감정이 얼마나 자주 판정됐는지 데이터로 추적할 수 있게 했습니다.

### 6. 지연시간: 병렬화와 짧은 TTL 캐시

자연어 메시지 하나당 Supabase 왕복이 순차로 10회 넘게 쌓여 실제 응답 속도의 병목이 됐던
걸 발견한 뒤, 서로 의존관계가 없는 DB 호출은 전부 `asyncio.gather`로 묶어 동시에 보냅니다
(예: 히스토리 조회+대화 상한 조회, 최근 맥락 조회+부름 이벤트 판정, 통계 갱신+로그 기록).

부름 이벤트는 하루 5번, 10분씩만 "활성" 상태인데도 매 메시지마다 DB를 조회하던 걸
5초 TTL의 인메모리 캐시로 대체했습니다 — 실제 클레임(`claim_call_event`)은 여전히 DB
레벨 원자적 처리라 캐시가 살짝 오래돼도 이중 지급 같은 정합성 문제는 생기지 않고, 그저
이벤트가 방금 마감된 걸 몇 초 늦게 알아채는 정도의 영향만 있습니다.

관리자 콘솔(`core/admin.py`)은 이런 최적화조차 필요 없도록 **처음부터 LLM 호출이 전혀
없는 순수 규칙 기반**(문자열 매칭 + DB 조작)으로 설계해, 권한이 있는 명령어일수록 오히려
가장 빠르고 예측 가능하게 동작합니다.
